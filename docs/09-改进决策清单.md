# SoftGraph 改进决策清单 —— 待决断项（v3.1.1 现状审计）

> 目的：列出当前**实现不完善或设计不合理**的点，每项给出「现状 / 问题 / 设计选项 / 建议」，
> 由维护者决断设计方向后再排期实现。标 🔴 的存在真实用户风险，建议优先。

---

## A. 规则体系（两个同根源的结构性缺陷）

### A1 🔴 规则内容无法更新（ensureRules 只追加缺失 id）
- **现状**：启动合并只把「本地没有的 id」追加进规则文件；已存在 id 的内容（根/模式/描述）永远不会更新。GC-14 扩根时就因此踩坑（AI IDE 根到不了老用户，被迫拆出 GC-16）。
- **问题**：每次改现有规则内容都要「新开 id」，规则编号会无限膨胀；Winapp2 导入的规则内容更新同样卡死。
- **选项**：
  - **A1-a**（推荐）：规则文件分区——`builtin`（随应用/热更新整体替换）+ `community`（Winapp2 导入区，可整体重导）+ `user`（用户自定义，永不覆盖）。加载时三区合并。
  - **A1-b**：每条规则带 `revision` 字段，合并时按 id+revision 高者胜。
- **建议**：A1-a，一次解决 builtin/community 两类更新。

### A2 🔴 清理规则版本号（kv）与实际文件脱节
- **现状**：`rules:version` 只在走在线更新流程时写入；手工/合并方式改了本地规则文件后 kv 不动。目前 kv=0 与实际 v5 内容并存，每次检查都会「重复更新一遍相同内容」（幂等但浪费且日志误导）。
- **选项**：A2-a kv 记录内容哈希而非版本号，更新前先比对哈希；A2-b 维持版本号但任何写入路径都同步 kv。
- **建议**：A2-a（哈希即真相，天然幂等）。

## B. 清理功能

### B1 🔴 GC-17 隐私清理：浏览器运行时清理会损坏数据
- **现状**：Chrome/Edge 运行时 Cookie/History 被锁定；扫描能列出，但清理可能失败，极端情况（Firefox jsonlz4 部分写入）会损坏会话。
- **选项**：
  - **B1-a**（推荐）：清理前检测 chrome.exe/msedge.exe/firefox.exe 进程，运行中则该类项标记「浏览器运行中，跳过」并提示；
  - **B1-b**：提示用户一键关闭浏览器后重试（危险度更高）。
- **建议**：B1-a，只做检测与跳过，不代杀进程。

### B2 重复文件（GC-11）扫描范围硬编码
- **现状**：根写死用户库四个目录；目录为空则恒为 0（已实际发生）。
- **选项**：B2-a 设置新增「重复/超大文件扫描目录」（用户自选，默认用户库）；B2-b 保持现状并在文档说明。
- **建议**：B2-a，顺带让 GC-12 超大文件也受益。

### B3 隔离区粉碎只有「全部粉碎」粒度
- **现状**：要么全粉碎，要么不动；没有按批次/条目选择。
- **选项**：B3-a 隔离区列表逐条勾选粉碎；B3-b 保持全部粒度（更安全的默认）。
- **建议**：B3-a 但保留双击确认；列表在隔离区管理页已有基础。

### B4 Winapp2 导入后的分类爆炸
- **现状**：700+ 节 → 700+ 条规则平铺进垃圾扫描分类列表，UI 无法浏览；且无「一键移除全部社区规则」「检查社区规则更新」。
- **选项**：B4-a 扫描页加「社区规则」折叠分组（与内置分组隔离）；B4-b 导入时按应用名聚合为少量大类。
- **建议**：B4-a（数据结构不动，纯 UI 分组），配合 A1 的 community 分区可做「重导/清空」。

## C. 升级管家（winget）

### C1 🔴 需要管理员权限的升级会静默失败
- **现状**：`winget upgrade --silent` 遇需提权的包直接失败（无 UAC），只报 exit code 非 0，用户不知道为什么。
- **选项**：C1-a 失败项标记「需要管理员」，提供「以管理员重试」（走现有 elevate 通道）；C1-b 先探测包是否需提权再统一提权执行。
- **建议**：C1-a，逐包处理粒度更细。

### C2 winget 文本输出解析是脆弱依赖
- **现状**：解析 `winget upgrade` 的人读表格（本地化列名、winget 版本升级改格式都会崩）。
- **选项**：C2-a 改用 `winget` 官方 PowerShell 模块（Microsoft.WinGet.Client，COM API，输出结构化对象）；C2-b 保持文本解析 + 健壮性回归测试锁行为。
- **建议**：C2-a（长期稳定），C2-b 作为过渡兜底（模块缺失时降级）。

## D. 更新体系

### D1 应用本体下载无镜像回退
- **现状**：electron-updater 只走 GitHub（85MB 直连基本必挂，代理是刚需）；规则包有 jsDelivr 回退，但安装包 85MB 超 jsDelivr 20MB 上限放不下。
- **选项**：
  - **D1-a**：接 Gitee Release 镜像（手动同步或 CI 同步），electron-updater `setFeedURL` 双源尝试；
  - **D1-b**：分卷安装包（NSIS web 安装器按需下载）——复杂度高；
  - **D1-c**：接受现状（文档写明需代理）。
- **建议**：D1-a，Gitee 同步脚本 20 行以内，收益/成本比最高。

### D2 检查频率策略粗糙
- **现状**：应用启动 30s 查一次 + 每 24h 一次，无「跳过此版本」「更新日志预览」。
- **选项**：D2-a 加「跳过此版本」记忆；D2-b 下载前展示 release notes。
- **建议**：D2-a+b 都小，可一起做。

## E. 交互与呈现

### E1 信任色标只差最后一公里
- **现状**：`signStatus` 数据在 FileDetail 里已有，图谱节点与详情页未着色。
- **建议**：图谱节点描边 + 详情页徽标（绿=已签名 / 灰=未签名 / 红=签名失效），工作量 0.5 天。

### E2 定时清理的可观测性
- **现状**：定时清理执行后只有日志，用户不知道「昨晚自动清了多少」。
- **选项**：E2-a 维护中心显示「上次自动清理：时间 + 项数 + 释放量」（kv 已有 lastRunAt，补读数）。
- **建议**：E2-a，0.5 天。

### E3 性能验证欠账
- **现状**：Winapp2 导入几百条规则后，全量扫描的规则编译/根遍历成本未基准验证（bench 只覆盖内置 17 类）。
- **建议**：bench 加「含 500 条社区规则」场景，量化了再决定是否需要规则惰性编译。

## F. 测试盲区
- **现状**：UI 层（SettingsDrawer / MaintenanceCenter / App）零自动化测试；本轮两次事故（迁移误删、send/handle 不配对）都是 UI 层且人工发现。
- **选项**：F-a 引入 @vue/test-utils 对关键组件做冒烟渲染测试；F-b 保持人工测试但建「发布前手测清单」。
- **建议**：F-b 先行（成本低），F-a 随 v3.2 引入。
