# 兼容性矩阵（C1 · Win10 22H2 / Win11 双基线）

> C1 的验收要求是「Win10 22H2 与 Win11 23H2 双基线回归」。缺 Win10 测试机这一条
> 短期内无法自行推进，但**「到位即测」的自动化准备**（v3.0.0 计划 1.1 项）此前一直没做，
> 本篇就是那份准备。机器到位后不需要人逐项手点，一条命令即可产出可横向对比的数据。

## 怎么采一台新机器

```powershell
# 管理员终端跑一次（普通权限也能跑，只是 USN 读取那一列会记为「不可用」）
npm ci
npm run compat:probe -- --with-smoke      # 探测 + 内核冒烟
# 需要连 GUI 端到端一起验（可选）：
npm run compat:probe -- --with-smoke --with-e2e
```

产出：

| 产物 | 位置 | 说明 |
|---|---|---|
| 完整报告 | `.tmp/compat-build-<build>-<hostname>.json` | UTF-8，逐项含 `ok` / `error` / 耗时 |
| 矩阵行 | 控制台末尾直接打印 | 复制成一行贴进下表即可 |
| 冒烟 / 端到端 | 报告内的 `smoke` / `e2e` 字段 | 含末尾若干行输出，便于定位 |

探测脚本：`tests/compat-probe.ts`。**每项探测互不阻塞** —— 任一能力缺失都记成
`{ok:false, error}` 继续跑完，因为「能力不全的机器」恰恰是最需要完整报告的那台。

### 列的含义与判定标准

| 列 | 采的是什么 | 什么算问题 |
|---|---|---|
| USN 查询 | `fsutil usn queryjournal`（**免提权**），按「可用卷 / 固定卷总数」 | 分子为 0 → 增量退化为纯目录签名，仍可发布，但需在发布说明写清 |
| USN 读取 | `fsutil usn readjournal`（**需提权**）。临时卷上先造一次真实变更（建文件再删）再回读，因此这一列同时证明**解析器认得这台机器的输出格式** | 未提权时分子为 0 属正常；提权后仍为 0 → 该卷无 USN 日志或系统限制 |
| API Set 条目 | 加载器动态映射（`api-set-normalized` 探测成功数） | 为 0 → 回退静态前缀表，依赖解析准确率下降，必须在验收报告注明 |
| KnownDLLs / SxS | 注册表 KnownDLLs 数 / WinSxS 程序集索引数 | SxS 为 0 → WinSxS 扫描被禁用或不可读，VC++ 运行库定位会退化 |
| RM(P-Invoke) | 用 Restart Manager 查**当前进程自己的 exe**，能查到本进程才算「正常」 | 异常 → 高度疑似 BUG-22（环境块过大导致 `Add-Type` 静默失败），**占用检测不可信**，属阻断级 |
| 长路径 | 注册表 `LongPathsEnabled` + 真实建一条 300 字符路径 | 建不出来 → 深层安装目录会被截断，需人工复核扫描与清理路径 |
| 符号链接 | 临时目录内建目录符号链接 | 失败只影响测试夹具与防逃逸自测（产品清理不建链接），非阻断 |
| 数据层驱动 | `openDb()` 实际选中的驱动与 FTS5 能力 | CLI 侧随 Node 版本变；**打包应用恒为 sql.js（无 FTS5）**，因此这一列不作为差异判据 |

## 本机（Win11 24H2 线）采出来的三处事实

1. **`ProductName` 不可信**：Win11 上它仍写作 `Windows 10 Pro`（兼容性垫片），
   所以矩阵的市场版本按 build 号判定（`≥26100 → 24H2 线`），脚本里写成 `friendlyName`。
2. **`LongPathsEnabled=0` 但 300 字符路径照样建得起来** —— 长路径能力已不只由该开关决定。
   这条数据的价值在于反向提醒：**不能**因为注册表是 0 就假设 Win10 上应用会截断，
   也不能假设 Win11 能建就一定等于 Win10 能建，必须实测（脚本正是这么做的）。
3. **本轮修复 BUG-35**：Restart Manager 的 `RM_PROCESS_INFO` 托管结构体与原生布局错位
   （用 C# `long` 表达 FILETIME 多出 4 字节对齐填充；`strAppName` 用了 256 而非 255）。
   后果是**第 2 条占用记录起 PID 全是垃圾值**，且 `Get-Process -Id <垃圾值>` 抛的是
   **终止性**参数绑定错误（`-ErrorAction SilentlyContinue` 拦不住），直接中断循环 ——
   表现为「多进程占用时只显示前一条，且界面上的占用者 PID 可能是错的」。
   单占用者的用例永远测不到这个坑（第一条的 `dwProcessId` 恰好在偏移 0），
   它是在兼容探测跑出 5 条记录时暴露的。回归用例：`tests/unit/locks.test.ts`
   「查自身可执行文件：必须看到本进程」。

## 人工验收清单（探测覆盖不到的部分）

C1 的完整验收 = 上面的自动探测 + 下面这份手点清单。GUI 相关项无法自动化。

- [ ] 首次启动：安装版与便携版各装一次，检查 SmartScreen 提示与杀软误报（风险 R8）
- [ ] 主界面：软件列表加载、图标显示（A2 按需队列在慢盘上的观感）、搜索与筛选
- [ ] 图谱：构建一个大型软件（如 Office / Visual Studio）的依赖图，检查收敛与交互帧率
- [ ] 垃圾清理：扫描 → 预览 → 隔离 → 还原 全链路，检查受保护路径不出现在结果里
- [ ] 注册表清理：扫描 → 勾选 → 三级确认 → 备份 → 删除 → 从备份还原
- [ ] 浮窗：多实例跨显示器分布（F4）、拖拽与靠边隐藏、穿透模式
- [ ] 深色/浅色主题与系统 DPI 125%/150% 下的文字截断
- [ ] Win10 特有：`fsutil` 中文输出解析（USN 原因字段本地化文案）、`SysWOW64` 判定
- [ ] 卸载后残留检查：`%LOCALAPPDATA%\SoftGraph` 是否按设计保留（`deleteAppDataOnUninstall: false`）

## 复采与刷新

- 探测脚本只读为主；唯一写入是临时目录与 `.tmp`（USN 那一项会在临时卷创建并删除一个临时文件）。
- Windows 更新后应重采一次：`build`、`API Set 条目`、`SxS 索引数` 都会变，矩阵按 build 号分行。
- CI 上每次构建都会产出一份 runner 机型的报告（`compat` 作业），
  这等于长期免费维护「另一台 Windows」的基线数据。
