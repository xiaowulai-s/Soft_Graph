### A7 依赖解析并行 —— 完成，但**原定方案被数据推翻**

**原计划写的是「PE 解析 worker 池」。分段实测（`tests/diag-deps-profile.ts`）显示这打错了靶子：**

| 分段 | 修复前累加 | 占比 |
|---|---|---|
| `snapshot`（安装目录快照） | 12497ms | **40.8%** |
| `bfs-dotnet`（E4 .NET 程序集定位） | 12930ms | **42.2%** |
| com / shortcut / prepare | 4372ms | 14.2% |
| **`bfs-parse` + `parse-main`（PE 解析）** | **108ms** | **0.3%** |

于是改做两件真正有效的事：

| # | 改动 | 说明 |
|---|---|---|
| A7-1 | **修 E4 的真实缺陷** | 原实现 `if (hits > 120) break` 统计的是**命中数**而不是处理数 —— 未命中的引用会把全部 ~10 个运行时目录穷举一遍，每条约 10 次注定失败的 `fs.access`。Docker Desktop（一个大型 .NET 应用）**12.9s 全耗在这里**，占其解析总耗时 99.6%，最终只产出 192 条边。改为「每个运行时目录 `readdir` 一次」建索引（进程内缓存）→ 语义等价（先到先得 = 原搜索顺序） |
| A7-2 | **快照并行化** | `snapshotInstallDir` 改为「**先按目录批量发起 stat，再按目录内原顺序消费**」。遍历顺序、`totalBytes` 累计顺序、`files` 排布、`maxFiles` 截断点全部与串行版一致 —— **可证等价**，而不是「应该一样」。只把同目录内的 stat IO 重叠起来（`SG_SNAP_CONCURRENCY`，默认 16） |
| 未做 | **PE 解析 worker 池** | 数据不支持（0.3%）。**不为关闭清单而硬做** |
| 新增 | `onStage` 分段计时回调 | 让「12.8s 花在哪」以后随时可复核，不必再靠印象 |

**结果（同机、同输入、5 样本累加）**

| 指标 | 修复前 | 修复后 |

| 总耗时 | 30701ms | **9881ms（−68%）** |
| Docker Desktop | 12980ms | **60ms** |
| Siemens NX / Quartus / Questa | 10231 / 3235 / 3311ms | 6395 / 1497 / 1461ms |
| `bfs-dotnet` | 12930ms | **11ms** |
| `snapshot` | 12497ms | 6290ms（−50%） |
| **图谱输出** | — | **逐项一致**：6053/6053/4 · 6021/6021/11 · 1140/1140/41 · 6023/6023/1 · 192/192/3（文件数/边数/解析成功数） |

用例：`tests/unit/snapshot-dir.test.ts` **7 条** —— 把**改造前的串行实现原样抄进用例当金标准**，

### I-11 路径检索（数据层 + UI）—— 完成

**先纠正文档里两处与事实不符的说法**（实测见 `tests/diag-file-search.ts`）：

| 原说法 | 实测 |
|---|---|
| 「路径检索退化为 LIKE + 前缀索引」 | 此前**两样都不存在**（全仓零处 `LIKE` / `fts5` 实现，也没有任何检索入口） |
| 「按驱动能力启用 FTS5」 | `sql.js` 报 `no such module: fts5`；`node:sqlite` 支持。**打包应用恒走 sql.js**（Electron 33.4.11 = Node 20.18.3，无 `node:sqlite`）→ FTS5 在正式包里**不可达**，只能是可选路径 |

| 查询写法 | 查询计划（20k 行实测） |
|---|---|
| `LIKE 'q%'` | `SCAN file_index` ← 索引完全用不上 |
| `lower(col) LIKE` | `SCAN file_index` ← 套函数必然废掉索引 |
| `col >= ? AND col < ?`（本项目主路径） | `SEARCH file_index USING INDEX idx_file_path_lc` ✅ |
| `name_lc` 前缀范围 | `SEARCH file_index USING INDEX idx_file_name_lc` ✅ |
| 子串 `%q%` | `SCAN file_index`（必然，无法用 B+Tree） |

| 项 | 结果 |
|---|---|
| 数据层 | 新增 `full_path_lc` / `name_lc` 两个**小写派生列** + 各自索引：写入侧算好、查询侧纯范围比较 → **大小写不敏感且走索引**（实测小写查询命中 2777 行 = 库中同前缀大写行 2777 行） |
| 检索 API | `store.searchFiles(query, { limit, mode })`：`prefix`（默认，两个索引各扫一段范围后在内存合并去重） / `substring`（显式启用）；返回 `strategy` 供 UI 如实提示代价 |
| **顺带修掉一个会让应用起不来的缺陷** | `idx_file_path_lc` 原本写在 `SCHEMA` 里，而老库的 `file_index` 没有该列 → `CREATE INDEX` 抛「no such column」→ **整个 `init()` 失败、应用无法启动**。两条 lc 索引改为只在 `migrateLc()` 里建 |
| 老库迁移 | `ALTER TABLE` 补列 → 有缺值才回填 → 建索引；幂等，可重复执行 |
| FTS5 分支 | 驱动支持时子串检索走 `MATCH`（`unicode61` 分词）；**不在写入路径维护** FTS 表，改「脏标记 + 首次检索惰性重建」—— 为一条生产环境永不执行的路径去改主写入链路不划算 |
| 真机 | 真实库 1075 行：`prefix-index` 策略，查询 0~1ms |
| UI | 顶栏新增「检索全库文件」：≥2 字防抖 300ms 检索、前缀/子串一键切换、结果下拉（文件名 + 完整路径 + 引用数），命中项**复用 D2 的 `graphDrilldown`** 打开反向子图 —— 不新建数据通路，因此能覆盖「当前软件图谱里没加载」的文件 |
| 用例 | `tests/unit/file-search.test.ts` **17 条**：**两条驱动分支都覆盖**（sql.js 无 FTS5 / node:sqlite 有 FTS5，后者缺失时自动跳过）、老库迁移、大小写不敏感、前缀 vs 子串语义边界、去重、limit、<2 字不检索、诊断快照 |

## 一、A2 图标提取懒加载

### 现状（代码依据）

1. `scanSoftware`（`main/services/scan.ts`）在 `done` 事件后对**全部**软件一次性 `extractIcons`；
2. `SOFTWARE_ICON` handler 只读 PNG，未命中返回 `null`；
3. 渲染层 `App.vue::loadIcons` 是 `for (const it of items) { await getIcon() }` —— **逐个串行 IPC**，且每次 `icons.value = {...icons.value, [hash]: d}` 触发**一次全量响应式重渲染**。

> 250 个软件 = 250 次 IPC 往返 + 250 次对象整体替换。**这其实是当前图标体验的真正瓶颈**，与「懒加载」正交。

### 方案

| # | 改动 | 说明 |
|---|---|---|
| A2-1 | 渲染层批量取图标 | `mapPool`（`@shared/util`，并发 8）一次取回，**单次赋值** `icons`。预计 250 项从「N×RTT」降到「1 批」 |
| A2-2 | 主进程图标按需队列 | `SOFTWARE_ICON` 命中即返回；未命中 → 按 hash 入队去重、立即返回 `null`；队列 **250ms 防抖聚批**后调一次 `extractIcons`（一次 PowerShell 处理整批） |
| A2-3 | 就绪推送 | 批次完成后向渲染层推 `software:icons`（`{hash: dataUrl}[]`，只推本批新提取的）。新增 preload 白名单与 `SoftGraphApi` 类型 |
| A2-4 | 预热降级为可选 | 扫描后的全量预热**保留**（纯懒加载会让首屏列表全是占位色块），但可通过 `SG_ICON_PREWARM=0` 关闭 |

**为什么不改成「一次性建 worker 常驻池」**：图标提取走 PowerShell + System.Drawing，单次调用可批量处理任意条数；聚批已经摊薄了进程启动成本，再加常驻池收益有限而复杂度显著上升。

### 验收口径

- 二次进入应用（PNG 已落盘）列表**无占位闪烁**；
- 首次冷启动滚动列表时，未命中图标按批到达，不出现整列表长时间空白；
- 队列去重生效：同一 hash 的 N 次请求只产生一次提取；
- 单测覆盖：队列去重 / 聚批合并 / 批次推送 / 未命中返回 null。

## 二、A3 便携目录 mtime 缓存

### 现状

`scanPortable` 已目录级并发 8；每个候选目录跑 `scorePortableDir`（readdir + `fs.access` + `readPeMeta(mainExe)`），命中项再并行 `dirSize(dir, 2, 3000)`。冷路径 **4.46s ≤ 6s 已达标**，因此 A3 的定位是**应用内二次扫描提速**，属纯优化 —— 正确性优先。

### 方案：目录级缓存 `cache/portable-scan.json`

```
key   = normKey(dir)
value = { sig, cand }
sig   = 目录 mtime + 条目数 + mainExe 路径 + mainExe mtime
```

| 设计点 | 决定 | 理由 |
|---|---|---|
| 签名含「目录 mtime + 条目数」 | 是 | 目录内**增删条目**会更新目录 mtime，能兜住 |
| 签名含「mainExe mtime」 | 是 | 文件**原地覆写不改目录 mtime**（A5 已确立的同一坑）—— 主 exe 被替换是最关键的变化 |
| 缓存命中时的开销 | 2 次 `stat` | **免去 readdir + readPeMeta + dirSize**，这才是收益来源 |
| `installedPaths` 变化 | **整体作废** | 「无卸载项」特征（+20 分）依赖已安装集合，装/卸一个软件就可能翻转判定 |
| `manualMarks` 与该目录缓存时的值不同 | 该条目重算 | 手动标记 +100 分，是权重最大的特征，绝不能沿用旧判定 |
| TTL | 7 天 | 兜住所有上面没覆盖到的角落 |
| `sizeBytes` | 存缓存值，标注「显示用」 | 目录内文件原地覆写导致体积变化时可能过期 —— 与 A5 已声明的边界同类 |

**已知边界（要同时写进代码注释与文档）**：目录内**文件被原地覆写**且体积变化时，`sizeBytes` 在 TTL 内可能沿用旧值；目录 mtime 与 mainExe mtime 都未变的情况下，评分不会重算（这是设计目标）。

### 验收口径

- 二次便携扫描耗时对比（真实根目录 A/B），结果**与全量扫描逐字段一致**（含 score / evidence / mainExe）；
- 手动标记切换后**立即生效**（必须有专门用例）；
- 已安装集合变化后缓存整体作废（专门用例）；
- 单测覆盖：签名判定（命中 / 目录 mtime 变 / mainExe mtime 变 / 条目数变）、指纹失效、manual 失效、TTL 过期、脏数据容错。

## 三、A7 依赖解析并行

### 现状（代码依据）

| 阶段 | 实现 | 并行度 |
|---|---|---|
| 阶段一 主程序 PE | `parsePe(sw.mainExe)` | 1 次 |
| **阶段二 目录快照** | `snapshotInstallDir`：递归 walk，逐文件 `await fs.stat`，≤6000 文件 / 深度 6 | **完全串行** |
| 阶段三 BFS 解析 | 层内 `for (const p of nextLevel) await parsePe(p)`，每节点限 40 | **串行**（调用次数少） |
| E6 / E7 | 磁盘缓存 + 内存索引 | 首轮一次性 |

**首要嫌疑是阶段二**（串行 stat 风暴），不是 PE 解析。文档原定的「worker 池并行 PE 解析」可能**打错了靶子**。

### 方案：先测量，再动手

| 步 | 内容 |
|---|---|
| **A7-0 测量（必做前置）** | 新增 `tests/diag-deps-profile.ts`：对「最大的已安装软件 / Docker Desktop（若存在）」分段计时（主 PE / 快照 / BFS 解析 / E6 / E7 / 打分），结果落 UTF-8 JSON。**没有这个数字就不许写并行代码** |
| A7-a 快照并发化 | 若阶段二占比高：`snapshotInstallDir` 改「目录级并发 + 信号量」，与 A6 `walkRule` **同口径**（`SG_SNAP_CONCURRENCY`，默认 8）。保持 `maxFiles` 截断与符号链接防逃逸语义逐字不变 |
| A7-b PE 解析 worker 池 | 若 `parsePe` 占比高：用 `node:worker_threads`（CPU 密集 + 可传 buffer，优于 `utilityProcess`；主进程可用）。**层内并行、层间串行** —— BFS 的 `parsedPaths` 去重与深度门控必须保序：把「本层待解析清单」一次性并发解析，再按原顺序入队 |
| A7-c 都不显著 | 如实记录并结项。**不为关闭清单而硬做** |

### 关键风险

- **并发 walk 的完成检测竞态**：BUG-11 的同类坑（根任务 stat 期间 `pending` 短暂为 0 被误判「已完成」）→ 用「同步预计数」而非 `pending === 0`；
- worker 需传递 `parsePe` 依赖的路径/环境上下文，且**不能再引入静态原生依赖**（架构守护用例会拦）。

### 验收口径

- 同一软件解析耗时**分段对比**（改前 / 改后），说明收益落在哪一段；
- 图谱输出**逐字段一致**：节点数 / 边数 / 每条边 confidence / evidence / 分组收纳数；
- 单测：并发快照与串行快照结果一致、截断行为一致、符号链接仍被跳过。

## 四、I-11 路径检索（数据层 + UI，用户已确认形态）

### 事实前提

FTS5 在**打包运行时不可达**（Electron = Node 20.18.3 → 无 `node:sqlite`；sql.js 无 FTS5）。因此 FTS5 是「**有则用、无则退**」的可选路径，**主路径必须是能在 sql.js 上工作的方案**。而实测表明该方案只有一种形态：**范围查询走 `idx_file_path`**（`LIKE 'prefix%'` 走的是 `SCAN`，索引用不上）。

### 数据层
