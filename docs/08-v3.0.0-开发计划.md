### B1-L2 `partial` 模式的排除依据（补全动作已完成）

文档原定的补全动作是「评估父文件 ID 反查路径的可用性与单次成本；可行则实现定向失效，否则明确放弃」。
新增诊断脚本 `tests/diag-usn-idlookup.ts`（只读系统调用）给出可复核数字：

| 观测项 | 结果 |
|---|---|
| 能力 | `fsutil file queryFileNameById <卷> <fileid>` —— **无需提权即可用**，3/3 命中并返回完整路径（G: 为 NTFS） |
| 单次成本 | **158ms**（152~163ms，n=3；进程启动占绝大部分） |
| 批量通道 | **无** —— 一次只接受一个 fileid，成本随变更条数严格线性 |
| 外推 | 按每轮 200 条变更 = **31.6s**，是签名遍历基线（GC-12 实测约 10.0s）的 **316%** |
| 结论 | **不可行**：为了省一次签名遍历要先付三次遍历的代价。**放弃 `partial`**，只保留 `reuse-all`，增量继续以「卷哨兵 → USN 零变更复用 → 目录签名」三级降级运行 |

> 重新打开此结论的前提是出现**批量反查**通道（一条命令解析多个 ID）；
> 单条调用在数量级上不可能翻盘。结论已固化进 `incremental.ts` / `usn.ts` 的代码注释。

> **A7 的关键教训（值得记住）**：文档原定的「PE 解析 worker 池」是凭结构印象写下的假设。
> 分段实测显示 `snapshot` 40.8% + `bfs-dotnet` 42.2%，而 `parsePe` 只有 **0.3%** ——
> 照原方案做会付出大量复杂度却几乎不改善耗时。**先测量再动手**省下的不只是一次返工。
>
> **I-11 的两处旧结论已纠正**：
> ① `store.ts` 注释称「路径检索退化为 LIKE + 前缀索引」——此前**两样都不存在**；
> ② `LIKE 'q%'` 的查询计划是 `SCAN`（索引用不上），`lower(col)` 更是直接废掉索引 ——
> 因此本项目改用「写入侧算好的小写派生列 + 纯范围比较」，`EXPLAIN` 可见 `SEARCH … USING INDEX`。
